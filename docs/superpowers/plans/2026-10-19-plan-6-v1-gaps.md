**Goal:** Close the most serious known v1 holes after v0.1.0: `cd <dir> && rm -rf *`
is not blocked, a stray nested `.saiife/config.toml` silently weakens the guard, and
small CI/docs leftovers.

**Tech Stack:** Rust workspace (`guard`, `cli` crates), GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-13-saiife-cli-v1-design.md` (§1.2 security
principles, §7.3 stated limitation, §7.5 tamper detection). Carry-over items are in
`docs/superpowers/plans/2026-10-13-saiife-v1-roadmap.md` ("Carry-over from plan 5b"
and "5c").

## Review Focus

1. `cd /tmp && rm -rf ./build` — a normal clean-up in a temp dir must stay allowed (Task 1 allow test).
2. `cd "$(mktemp -d)" && rm -rf *` — unresolved `cd` target: decide and pin (Task 1: treat as unknown dir → same as today, no new deny).
3. `cd / ; rm -rf *` and `cd ~ || exit; rm -rf .*` — `;` and `||` sequencing (Task 1 deny tests).
4. A project with 50k files (node_modules) — the nested-config scan in `status` must stay bounded (Task 2 test with a limit).
5. `(cd / && rm -rf *)` and `bash -c 'cd / && rm -rf *'` — subshell and nested shell (Task 1 deny tests; the cwd change must not leak out of a `( … )` subshell into the next command).

### Task 1: Track `cd` within a command line

**Files:**
- Modify: `crates/guard/src/engine.rs` (`ShellState`: add the effective cwd for the rest of the current list; update on `cd`/`pushd`/`popd` segments)
- Modify: `crates/guard/packs/core.filesystem.toml` only if a rule needs the resolved form
- Test: `crates/guard/tests/corpus_filesystem.rs` (new cases), `crates/guard/tests/corpus_chaining.rs`
- Modify: `docs/packs/core.filesystem.md` (remove `cd / && rm -rf *` from Not covered; add the new limits), roadmap

**Behaviour:**
- After a `cd X` / `pushd X` segment joined by `&&`, `;`, `||` or a newline, later segments in the same list are judged as if their relative path operands were prefixed by X. `X` of `/`, `~`, `$HOME`, `~/`, `..` chains that resolve to `/` or `$HOME`, or `-` (unknown) are handled: `/`, `~`, `$HOME` resolve; `-`, `$(…)`, unset variables and anything unresolvable make the cwd **unknown**, and unknown keeps today's behaviour (judge the operand as written).
- A `( … )` subshell gets its own copy; its `cd` does not affect segments after the `)`. `bash -c '…'`/`sh -c` inline payloads already recurse — they start with the outer effective cwd.
- Mechanism (choose the simplest that the engine supports): rewrite the operand of destructive filesystem commands (`rm`, `find … -delete`, `shred`, `chmod -R`, `chown -R` — whatever core.filesystem's rules cover) to the joined absolute form before rule matching, e.g. `rm -rf *` after `cd /` is matched as `rm -rf /*`. Do not change how non-filesystem packs see the command.

- [ ] **Step 1: Failing tests** (deny unless marked allow):
  - `cd / && rm -rf *`, `cd /; rm -rf *`, `cd ~ && rm -rf *`, `cd $HOME && rm -rf .`, `cd ~ || exit; rm -rf .*`, `(cd / && rm -rf *)`, `bash -c 'cd / && rm -rf *'`, `cd /usr && cd .. && rm -rf *`
  - allow: `cd /tmp && rm -rf ./build`, `cd build && rm -rf *` (relative cd into a project subdir), `(cd / && ls) && rm -rf ./dist`, `cd "$(mktemp -d)" && rm -rf *` (unknown cwd → today's verdict, pin whatever it is today)
- [ ] **Step 2:** Run `cargo test -p saiife-guard` — new deny cases fail.
- [ ] **Step 3:** Implement.
- [ ] **Step 4:** Run the full workspace tests, `refactor_equivalence`, `shell_differential`; list any verdict changes outside the new cases in the report (expected: none).

### Task 2: `status` finds nested configs without an integrity record

**Files:**
- Modify: `crates/cli/src/status_cmd.rs`
- Test: `crates/cli/tests/status_cmd.rs`
- Modify: `docs/agents/*.md` or `docs/threats.md` where status checks are listed; roadmap

**Behaviour:**
- `status` walks the project tree from the project root looking for `.saiife/config.toml` files below it, skipping `.git`, `target`, `node_modules`, and any directory it cannot read, without following symlinks, stopping after 20 000 directory entries.
- For each nested config whose directory has no integrity record: `WARNING: <rel>/.saiife/config.toml is a separate saiife config that was not set up with saiife init; hooks run in <rel> use it instead of this project's config.` with `Fix: delete it, or run saiife init in <rel>`. It counts as a failed check (exit 1).
- If the walk stops at the limit: a note `nested-config scan stopped after 20000 entries` (not a failure).
