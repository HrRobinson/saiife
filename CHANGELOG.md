# Changelog

## 0.2.0 — unreleased (waiting for red-team suite)

- Locked mode on macOS (v2.1): `sudo saiife system install` works on macOS 15 or later, Apple silicon and Intel. It creates the hidden `_saiife` user and group and the `_saiifeaudit` group with `dscl`, runs `saiifed` as the launchd daemon `com.saiife.saiifed` (stderr in `/var/log/saiife/daemon.log`), keeps state in `/var/db/saiife`, the vault key in `/var/db/saiife/keys/vault.key` (`daemon_file`, 0400) and the sockets in `/var/db/saiife-run`, writes the managed hooks for Claude Code (`/Library/Application Support/ClaudeCode/managed-settings.d/`), Codex and Gemini CLI, and registers the authorization right `com.saiife.approve`. The daemon reads the peer uid with `LOCAL_PEERCRED`; the pid (`LOCAL_PEERPID`) and the process names (`sysctl(KERN_PROC_PID)`, in the new `saiife-darwin` crate, the only crate allowed `unsafe`) are attribution only. Same-user approval is off on macOS: the prompt cannot show what is approved, so `same_user = "reauth"` acts as `"deny"` and approvals need a second account. Install requires the hardened runtime and warns on an ad-hoc signature; tagged releases with the signing secrets are signed with a Developer ID and notarized, other builds are ad-hoc signed and say so in the release notes. `doctor` gains the macOS checks (launchd, signature, auth right, `_saiifeaudit`, the Claude MDM profile). The MCP gateway stays Linux only (`[mcp.*]` is a load error on macOS); `saiife mcp` works. `run --secret` and `run --cloud` work, `DYLD_*` is removed from the command's environment on every platform, and a `run_allow` entry through `/etc`, `/var` or `/tmp` is refused on macOS with a `/private` hint. `core.lock` denies `security authorizationdb` writes and `dscl`/`dseditgroup` on `_saiife*`. `saiife daemon --user` works on macOS (sockets in `~/Library/Caches/saiife/run`, the login Keychain). Lock labels are per platform; every macOS label is `unverified` until the new `scripts/lock-check/macos-vm.sh` is run in a macOS VM. See `docs/install.md`.
- Fleet packaging (Linux): `.deb` and `.rpm` packages (amd64/arm64, rpm signed when the key is set) whose scripts run the new `saiife system install --fleet`, which reads `/etc/saiife/fleet/config.toml` and `install.toml`; a changed config now reloads a running daemon, and install exits 1 when the daemon did not take it; `doctor` gains `files.package` and an `agents` warning; the release adds `SHA256SUMS` over all assets and `SHA256SUMS.asc` when signed; an Ansible role and an Intune Linux compliance policy. macOS `.pkg` and MDM recipes follow plan 13. See `docs/fleet.md`.
- MCP (Linux): `saiife mcp` is a stdio MCP server that lists brokered connector operations (`shopify_orders_list`) and gateway tools (`linear__create_issue`) as tools and sends every call through the daemon's pipeline (`via = "mcp"`); `saiife_result` fetches a pending result and `--wait` waits for an approval. The MCP gateway (locked mode only) runs third-party stdio servers declared as `[mcp.<name>]` under the daemon, with their tokens in the vault, a Landlock sandbox (`saiife __mcp-spawn`), per-tool `allow`/`ask`/`deny`, limits and one `connector` record per call; results are masked and cut at `max_response_bytes`. Approvals gain the type `mcp`. The gateway child's network is not sandboxed. `system install` writes the Claude Code managed MCP allowlist drop-in `60-saiife-mcp.json` from policy (it replaces `--mcp-allow`); `doctor` and `status` gain the MCP checks. Codex and Gemini MCP servers are restricted by the hook only. On Codex and Gemini CLI, `saiife mcp` needs `[guard.mcp] allow_servers = ["saiife"]`, and that listing is unpinned: any server registered as `saiife` is allowed. See `docs/mcp.md`.
- Cloud connectors: Amazon S3 and STS (`aws-s3`, `aws-sts`), Google Cloud Storage (`gcp-storage`), Azure Resource Manager (`azure-arm`) and Azure Blob Storage (`azure-blob`). In `mode = "sign"` (the default) the daemon signs each request with AWS SigV4, or attaches an OAuth2 token it mints from a `gcp_sa` or `azure_sp` secret; the agent never sees a credential. Capabilities follow the IAM action. New vault kinds `aws`, `gcp_sa` and `azure_sp`; object keys may contain `/` (`objectkey`, `objectname`); the cloud key shapes are masked. Each connector has a docs page; see `docs/connectors/README.md`.
- STS mode (AWS only, opt-in): `saiife run --cloud <service> -- <command>` runs the command with an `sts:AssumeRole` credential of 900 s and an inline session policy built from the saiife policy (a project overlay can only narrow it). This hands a credential to agent-controlled code: any process of your user can ask the daemon for a lease, and the `run_allow` check binds only the `saiife` client. `doctor` warns for every service in STS mode. Only `requests_per_minute` applies to leases. Each lease is a `secret` record with `event = "cloud_lease"`. See `docs/connectors/aws-s3.md`.
- Personal broker (Linux): `saiife daemon --user` runs the broker as your own user, with the vault key in the Secret Service (GNOME Keyring, KWallet) and `vault.bin` sealed under it. `--print-unit systemd|launchd` prints a login unit. Not a security boundary: a script of the same user can read the key. The audit chain is unsigned and `saiife audit --broker` reads it; `secret import` and `audit.rotate_key` are refused; macOS is refused until the v2.1 daemon port. New `saiife-keychain` crate (Secret Service over zbus, macOS Keychain backend compile-checked). `core.self` and `core.secrets` gain mistake-layer rules for the broker. See `docs/personal-broker.md`.
- Locked mode, with the personal broker: the CLI commands that talk to the locked daemon (`secret`, `connect`, `api`, `run --secret`, `approvals`/`approve`/`reject`, `lockdown` and the locked `saiife audit` query) now require the daemon's hello to say `mode = "locked"`; a broker or older daemon on that socket is refused. `saiife audit verify` on a keyless chain whose genesis says `locked` prints "locked mode: no signing key" (it said "developer mode"); a personal broker chain says "personal broker". The locked `saiife audit` query now goes through the shared resolver: a system config without `locked = true` is refused with "<config>: locked is not true", and a daemon that does not answer as locked is "cannot reach the saiife daemon: …".
- Connectors, waves 2 and 3: Stripe, Slack, Discord, Linear, Intercom, Airtable, GitLab, Sentry, PagerDuty, Zendesk, Segment, WooCommerce, Salesforce and Email (SMTP send, IMAP read). Each has a docs page with a suggested policy that puts every write under `ask`; Stripe and WooCommerce refunds have amount caps. Manifests gain host parameters, built bodies (form, GraphQL, text), pagination and prefixed auth headers. See `docs/connectors/README.md`.
- OAuth2 secrets (`saiife secret add --kind oauth2`, paste flow): the daemon refreshes access tokens itself, keeps them in memory and persists a rotated refresh token before using it. `saiife run --secret` refuses an oauth2 secret (`run_not_allowed`): it is for connectors only, and its refresh token is never handed out.
- Masking: the audit masks the token shapes of the new services (Stripe `sk_`/`rk_` keys and `whsec_` signing secrets, Slack `xox*-`, `xoxe` and `xapp-` tokens, Slack and Discord webhook URLs after their host path, Discord bot tokens, Linear `lin_api_`/`lin_oauth_`, Sentry `sntrys_`/`sntryu_`, GitLab `glpat-` and the other `gl*-` prefixes, Salesforce session ids, Intercom tokens, Airtable `pat…`, WooCommerce `ck_`/`cs_` keys), also when glued to other text.
- Environments: `[environments.<name>]` adds packs and overrides service settings; in locked mode an environment is bound to a scope (`[[scope]] env`) and is part of the policy hash. New `saiife env list|use`; `env use --scope` is root only. See `docs/environments.md`.
- Environments in developer mode and under the personal broker: the project's `env` (`saiife env use`) selects the environment of `saiife api` calls; an environment changes connector calls only there, and its guard packs apply in locked mode (a developer-mode `policy show` says so). A well-formed `env` that no environment defines falls back to the base config with a warning (in locked mode the project's `env` is ignored). `env --system-config <file>` means locked mode and refuses a file without `locked = true`.
- `saiife status` and `saiife policy show` print the policy hash of each environment (`policy (env <name>): sha256:…`) beside the base one, so a record's `policy` names the environment it ran under; `policy show` shows a non-admin only their own environment's hash.
- The managed hook applies the caller's scope environment (its packs, and its hash in the record). Only when some scope binds an `env` does it look up the caller's groups: from `/etc/group` when the user is local and `nsswitch.conf` takes groups from `files` alone, otherwise through NSS (`getent`/`id`). A lookup that fails denies the call as `error_denied` with policy `unavailable`, recorded like any other failure; `env list` and the daemon's `policy.show` fail the same way rather than show "no environment".
- An approved connector request is sent under the environment it was asked under, or not at all: a locked scope rebound to another environment, or a developer-mode environment no longer defined, makes the send `send_failed` with `env_changed`. `approvals show`, the list and the `approval_created` notification name the environment. A request stored with no environment (the base config, or sealed before environments existed) is not checked.
- Environments under the personal broker: the HTTP gateway (`gateway.sock`) runs every call under the base config, not the project's `env`; only `saiife api` sends the project's environment, so agents should use it. Binding an environment to an `api token` is a later item.
- Collections: `saiife api collection list|run` runs saved calls from `.saiife/collections/`; each step goes through the full pipeline. See `docs/collections.md`.
- `saiife connect` refuses a host parameter that is not a bare lower-case hostname, instead of writing a policy file that would not load. `policy check` no longer warns "matches no operation" for a concrete qualifier rule such as `messages:read:channel=C0123`.
- Audit forwarding (Linux, locked mode): the daemon sends a copy of the audit to syslog (RFC 5424, also over TLS), to a file, or to an HTTPS endpoint (batches, Splunk HEC). Each target has its own cursor and delivery is at-least-once. Configure it with `[audit.forward.*]`. See `docs/forwarding.md`.
- New `saiife audit verify --external <file|dir>`: compares the local chain with a forwarded copy, so a cut or rewrite of records that were already forwarded shows.
- Auditors: the `saiife-audit` group reads the audit, and a per-user `audit.query` lets others query their own records through the daemon. `saiife audit` gains `--kind` and `--service`. See `docs/auditors.md`.
- New `saiife policy check|test|show|reload`: validate a policy (including overlapping scopes), run its `[[example]]` entries (exit 1 on a mismatch), print the merged policy and its hash, and reload it (admin).
- `saiife audit --report` gains sections for connectors, approvals, `error_denied`, daemon restarts and forwarding outages.
- Docs: threat coverage for each of the four setups, an egress recipe (nftables) with a `doctor` hint, forwarding and auditors pages.
- CI: the `locked-linux` job runs a locked end-to-end demo.
- Carry-over fixes from plans 10 and 11 (approval outcome in the report, open outages, section filters, stricter forward target validation, forwarder resume after a chain restart, polkit and install edge cases).

- Locked mode (Linux): approvals. A connector capability in a service's `ask` list, or a command denied by a rule in the new `[guard] ask`, waits for a person in `[approval] approvers`. `saiife api` exits 3 with the request id (`--wait` polls for the result, `saiife api result <id>` fetches it; HTTP answers 202 and `GET /v1/requests/{id}`). New `saiife approvals [show]`, `saiife approve` (`--accept-truncated`) and `saiife reject`. `same_user = "reauth"` lets one person approve their own requests through polkit (`com.saiife.approve`); the default `"deny"` needs a second account. An approved command becomes a one-use grant for that exact command in the project, for 15 minutes. At most 20 pending requests per user. See `docs/approvals.md`.
- Guard records keep `rule` (the regex) and gain `rule_id`; only `core.git`, `db.postgres` and the Kubernetes delete-namespace rule have ids in v2.0.
- New `[notify]`: webhook, SMTP and command targets for `approval_created`, `limit_reached`, `error_denied_burst`, `chain_break` and `lockdown` (`forward_failing` is defined; nothing sends it yet). Masked one-line summaries only, never a body or a secret. See `docs/notifications.md`.
- New `saiife lockdown on|off` (root, `[admin]` groups and approvers): denies connector requests, or with `--scope all` every hook call too. It survives restarts and is recorded and notified. See `docs/threats.md`.
- `saiife doctor` warns when re-authentication is unavailable.

- Locked mode (Linux) gets an encrypted vault and a connector gateway. New `saiife secret add|list|rotate|remove|import` store credentials (token, basic, header) in a vault the agent cannot read; `import` moves plaintext credentials out of a home and keeps a 7-day backup. New `saiife connect <service>` writes a deny-all policy file; with `--secret <name>` it reuses an existing secret that allows the service.
- New `saiife api <service> <operation>`: the daemon checks the call against the policy and limits, adds the vault credential, sends it and masks the answer. Connectors for Shopify, HubSpot, GitHub and a generic HTTP service; see `docs/connectors/README.md`.
- New HTTP gateway on `gateway.sock`, and an optional loopback TCP listener with `saiife api token` (12 h bearer tokens bound to your uid).
- New `saiife run --secret`: runs a command from the daemon's `run_allow` list with a leased secret in its environment, and masks its output.
- Requests per minute, writes, deletes, bulk and amount limits per service; the `connector` audit record.
- The control socket's answers may be up to 16 MiB; requests stay at 1 MiB.

- Audit records are now v2: each carries a sequence number and the SHA-256 of the previous line (a hash chain), plus kind, mode, host and policy. 0.1.0 can still read them.
- New `saiife audit verify` checks the chain (exit 0 intact, 1 broken, 2 unreadable).
- `saiife audit --report` gains Audit chain, Policy in force and Mode per host sections.
- `error_denied` now counts as blocked in `saiife audit`, `--blocked` and the report.
- A project `.saiife/config.toml` that is not a regular file (a FIFO or device, also when reached through a symlink) or is over 64 KiB is not read: the default packs apply, with a warning.
- A project `.saiife/config.toml` symlinked to a file outside the project is refused (never opened or quoted), by the hook and by `saiife init`; links that stay inside the project still work.
- New `saiife daemon --system` (Linux): the locked-mode daemon. It is the single writer of the audit log, stamps every record's time and identity, and signs checkpoints with an Ed25519 key.
- New `saiife check --managed` (Linux): the locked-mode hook. The guard runs in a separate worker process, and the call is allowed only after the daemon has recorded it. Every error (a worker crash or hang, a daemon that is down, slow or refuses, a policy that cannot be loaded) blocks the call: it fails closed.
- `saiife audit verify` checks checkpoint and key-rotation signatures.
- `saiife init` and `saiife status` read the project config with the same bounded, race-free read as the hook.

- New `sudo saiife system install` and `sudo saiife system uninstall` (Linux): set up or remove locked mode on Ubuntu 22.04+, Debian 12+ and RHEL 9+ (Rocky, Alma) with systemd. Install creates the `saiife` user and groups, puts the binary in `/opt/saiife/bin`, writes `/etc/saiife`, the vault key and the `saiifed` unit, adds managed hooks for Claude Code, Codex and Gemini CLI, starts the daemon and runs `saiife doctor`. Exit 2 on an install error or an unsupported system, 1 when installed but `doctor` found a failure. Uninstall removes exactly what install listed; `--purge` also removes the state, the audit and the users.
- New `saiife doctor [--user <name>] [--json]`: checks the machine locked mode relies on (files, owners and modes, keys, daemon, agent users, sudo and root-equivalent groups, plaintext credentials). Exit 0 all pass, 1 a warning, 2 a failure.
- New `core.lock` pack, on in locked mode: protects saiife's own install (`/etc/saiife`, `/opt/saiife`, the state, audit and socket dirs, the unit and the managed agent settings).
- New `saiife check --managed --event config-change`: Claude Code's ConfigChange hook. A change to user, project or local settings that sets a locked key is denied.
- Locked mode denies MCP tools whose server is not in `[guard.mcp] allow_servers`. `doctor` and `status` warn about each listed server: its requests are not brokered or limited.
- Under a managed hook, the project hook of that agent goes quiet (no double judging, no second record).
- Developer mode can opt in to fail closed with `[guard] fail = "closed"` in `/etc/saiife/config.toml`.
- `saiife status` shows a Locked mode block: mode, daemon health and chain head, policy hash, each managed agent's lock label and the MCP warnings. In locked mode `saiife init` writes no project hook for an agent with a managed hook, and `saiife init --off` keeps the project config.
- Lock labels: Claude Code is lockable; Codex and Gemini CLI are unverified (managed hooks are installed, `doctor` warns).

## 0.1.1 — 2026-10-19

- Guard: `rm` targets are judged against a `cd` earlier in the same command line (`cd / && rm -rf *` is now blocked).
- status: warns about nested `.saiife/config.toml` files that `saiife init` did not create.

## 0.1.0 — 2026-10-19

First release.

- 13 guard packs: filesystem, git, secrets, self-protection, Docker, Kubernetes, AWS, Azure, Google Cloud, Terraform, Postgres, MySQL and MongoDB. Each has a docs page in `docs/packs`.
- Audit log of every decision, with secrets masked. Read it with `saiife audit`.
- `saiife audit --report` writes a self-contained HTML report that a non-developer can read.
- `saiife init`, `saiife init --off` and `saiife status` for Claude Code, Codex and Gemini CLI. `status` detects when a hook or config was changed.
- Agent docs in `docs/agents`, a Codex with Ollama recipe, and a demo script.
- Prebuilt binaries for Linux and macOS (Intel and ARM), and `install.sh` with checksum verification.

Known limit: the Codex and Gemini CLI hooks are not yet verified against live installs.
